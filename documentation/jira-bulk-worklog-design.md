# Jira bulk worklog logger — design document

**Status:** specification complete, ready to implement
**Target:** Python desktop application, single file, Tkinter

This document is self-contained. An implementer should not need any prior conversation to build from it.

---

## 1. Problem

The user logs work against 3–6 Jira issues per day. Doing this through Jira's own Log Work dialog means navigating to each issue separately and repeating a modal interaction 6 times. The goal is one window where all of the day's entries are filled in, then committed with a single click.

The set of loggable issues is small (~25) and stable for ~6 months at a time, because they represent tracking goals rather than day-to-day tickets. 8 of the ~25 are subtasks of a parent issue, and time must be logged against the subtasks, not the parent.

## 2. Non-goals

These were considered and deliberately excluded. Do not add them.

- **No "what's already logged today" view.** The user has a Jira dashboard for this. *(Reversed on 7 August 2026 — see §17, "Logged work tab". The rationale below still holds for the log-entry screen; what was added is a separate tab for auditing past days, which is a different job.)*
- **No timer / stopwatch.** Entries are typed after the fact.
- **No daily hours target or under-logging warning.** A running total is displayed, but nothing is validated against it.
- **No bulk worklog endpoint.** A private one exists but requires ASAP service-to-service auth and is inaccessible to normal integrations. One HTTP request per row is correct and expected.
- **No OAuth.** This is a personal-use tool; an API token is the right auth.
- **No offline mode.** See §5 — the app hard-fails without network by design.
- **No browser extension.** Evaluated and rejected: the bulk end-of-day workflow means the user is not on an issue page when logging, so an extension's context-awareness advantage does not apply, and cookie-based auth is deprecated on Jira Cloud.

## 3. Stack and dependencies

- Python 3.11+ (`tomllib` and `zoneinfo` are stdlib from 3.11)
- Tkinter / `ttk` for the GUI (stdlib)
- `keyring` for credential storage
- An HTTP client (`requests`, or stdlib `urllib.request` to stay dependency-light)

Single-file script. No build step.

## 4. Jira API

Target is **Jira Cloud**, REST API **v2**.

> **Use v2, not v3.** In v3 the worklog `comment` field must be an Atlassian Document Format object — a nested `doc` → `paragraph` → `text` structure. v2 accepts a plain string, which makes multi-line comments trivial (`\n`). There is no benefit to v3 here.

### Authentication

HTTP Basic with `email:api_token`, base64-encoded:

```
Authorization: Basic <base64("user@example.com:API_TOKEN")>
```

The token is generated by the user at `id.atlassian.com` → Security → API tokens. It is **not** the account password. Store it via `keyring`; never in the config file or on disk in plaintext.

On first run, if no token is found in the keyring, prompt for email + token, verify with a single `GET /rest/api/2/myself`, and store on success.

### Endpoints used

| Purpose | Call |
|---|---|
| Verify credentials | `GET /rest/api/2/myself` |
| Validate ticket list + fetch titles | `GET /rest/api/2/search?jql=key in (...)&fields=summary,parent&maxResults=100` |
| Create worklog | `POST /rest/api/2/issue/{key}/worklog?adjustEstimate=leave` |
| Delete worklog (optional undo, see §14) | `DELETE /rest/api/2/issue/{key}/worklog/{id}?adjustEstimate=leave` |

### Worklog request body

```json
{
  "timeSpentSeconds": 9000,
  "started": "2026-08-06T11:00:00.000+0200",
  "comment": "Reviewed the auth PR.\nPaired with Anna on the retry logic."
}
```

### Three API details that will cause silent failures if missed

**1. `adjustEstimate=leave` is mandatory.** Without it Jira decrements the remaining estimate on every log. These are long-running goal tickets; their estimates must never be touched. Apply it to the DELETE as well.

**2. The `started` format is rigid:** `yyyy-MM-ddTHH:mm:ss.SSS±HHMM`. Milliseconds are required. The UTC offset must have **no colon** (`+0200`, not `+02:00`). Jira rejects deviations with an unhelpful error.

**3. Send `timeSpentSeconds`, not `timeSpent`.** The string form (`"2h 30m"`) is parsed by Jira using the instance's working-day and working-week configuration, so `1d` may not mean 24h. Since the app must parse durations locally anyway to compute the running total, send integer seconds and remove the ambiguity.

### Error handling

- `401` — token invalid or revoked. Prompt to re-enter; clear the keyring entry.
- `403` — authenticated but lacking the **Work On Issues** permission on that project.
- `404` — issue does not exist, or is not visible to this account.
- `429` — rate limited. Jira Cloud uses a dynamic cost-based budget rather than a fixed request-per-minute figure, and returns a `Retry-After` header in seconds. Honour it. At 3–6 requests per batch this should never trigger; handle it anyway rather than crashing.
- `5xx` / timeouts — treat as a row-level failure, retryable (§11).

## 5. Startup sequence

Strictly ordered. Any failure aborts with a plain-language message; the app does not open in a degraded state.

1. **Load config** from `~/.config/jira-logger/tickets.toml`. Missing or malformed → abort with the parse error and the expected path.
2. **Load credentials** from keyring. Absent → first-run prompt (§4).
3. **Validate credentials** via `GET /rest/api/2/myself`. Retain the returned `accountId` and `timeZone`.
4. **Validate the ticket list** with the single JQL `key in (...)` search covering every key in the file, active and retired. Populate each ticket's title from `fields.summary`.
   - Any key absent from the response is nonexistent or invisible to this account → abort, naming the offending keys.
   - Note: JQL visibility does not prove *Work On Issues* permission. A ticket can validate here and still fail with `403` at submit time. This is acceptable and handled per-row.
5. **Network failure at any of steps 3–4 → abort.** This is deliberate. Titles come exclusively from the API; there is no fallback to file-stored titles. An empty title is therefore impossible in a running app, and the absence of connectivity is surfaced immediately rather than producing a window that cannot submit.
6. **Warn if** `myself.timeZone` differs from the configured `timezone` (§6). Jira buckets worklogs by the *profile* timezone, so a mismatch shifts entries in reports. Warn, do not block.
7. **Restore draft** (§12).

## 6. Config file

Path: `~/.config/jira-logger/tickets.toml`

```toml
base_url = "https://yourcompany.atlassian.net"
timezone = "Europe/Warsaw"

retired = ["PROJ-3980", "PROJ-3981"]

[groups]
"PROJ-4400 · Platform reliability" = ["PROJ-4471", "PROJ-4472", "PROJ-4473"]
"H2 developer experience" = ["PROJ-4488", "PROJ-4489"]
"Unparented" = ["PROJ-4512"]
```

Notes for the implementer:

- **Keys only — no titles.** Titles are always live from the API (§5.5). Storing them would create a second source of truth that silently goes stale.
- **TOML rather than JSON** specifically so the user can leave `#` comments explaining what each goal covers.
- **Group labels are arbitrary user-chosen strings.** They need not mirror Jira's issue hierarchy. They exist for the picker's visual grouping only (§9).
- **`retired` keys remain selectable** but are collapsed in the picker. A key may appear in a group and in `retired` simultaneously; `retired` wins for display purposes. This matters because the week goals rotate is exactly when the user needs to back-log a few days against the previous set.
- `timezone` is an IANA name. Default to the system local zone if omitted.

## 7. Layout

Single window, roughly:

```
┌──────────────────────────────────────────────────────────┐
│  Date: [ 2026-08-06 ▾ ]                    Total: 7h 15m │
├──────────────────────────────────────────────────────────┤
│  [ ticket picker ▾ ]  [ comment (multi-line) ]  [ 2h ] ✓ │
│  [ ticket picker ▾ ]  [ comment (multi-line) ]  [ 45m ] ⨯│
│      └ error message, if failed                          │
│  [ ticket picker ▾ ]  [ comment (multi-line) ]  [    ] ✕ │
│  [ ticket picker ▾ ]  [ comment (multi-line) ]  [    ] ✕ │
├──────────────────────────────────────────────────────────┤
│  Ctrl+Enter submits         [Clear]  [Submit 2 entries]  │
└──────────────────────────────────────────────────────────┘
```

- **4 rows on open.**
- Comment field is multi-line (a small `Text` widget, ~3 lines visible, scrolling beyond).
- **Locked rows collapse to a single summary line** once logged, reclaiming vertical space at the point the row stops being editable. Six expanded comment boxes otherwise make the window unmanageably tall.
- Right-hand status glyph per row: pending / submitting / logged / failed.
- **Per-row remove control (`✕`) on unlocked rows only.**
- Keyboard flow matters — this is used daily. Tab moves between fields; `Ctrl+Enter` submits. (`Enter` must insert a newline inside the comment box, so it cannot also mean submit.)

## 8. Row model and validation

Each row holds: `ticket_key`, `comment`, `time_text`, plus derived `state`, `error`, `worklog_id`.

### Row states

| State | Meaning | Editable |
|---|---|---|
| `empty` | all three fields blank | yes |
| `partial` | some but not all three filled | yes |
| `ready` | all three filled and time parses | yes |
| `submitting` | request in flight | no |
| `logged` | committed; holds `worklog_id` | no (locked) |
| `failed` | attempted and rejected; shows `error` | yes |

### The empty/partial rule — get this exactly right

- **`empty` rows are skipped silently.** Never sent, never counted in the total, never counted in the submit button's label.
- **`partial` rows block the submit entirely.** They are *not* skipped.

The reasoning: silently skipping a half-filled row means the batch reports success while quietly dropping an entry the user intended to log. They would only discover it at review time, long after forgetting the details. Blocking surfaces it while the context is still fresh.

On a blocked submit: highlight every partial row, state what each is missing, and send nothing at all. No partial batch.

**Comments are required.** Jira treats the worklog comment as optional; this application does not. The user does not want time logged without a description, nor a description without time. All three fields are mandatory for a row to be submittable.

### Time parsing

- Accept `2h`, `30m`, `2h 30m`, `1.5h`, `90m`. Case-insensitive, tolerant of missing spaces.
- **Reject `d` and `w` units.** Their meaning depends on the Jira instance's working-day configuration, and nobody logs a full day against a goal ticket in this workflow. A clear rejection beats an ambiguous conversion.
- Parse to integer seconds. A value that does not parse puts the row in `partial`.
- Reject zero and negative durations.

### Auto-append

When the last row transitions out of `empty`, append one blank row beneath it. Maintain **exactly one trailing blank row** — if the user deletes content back out, collapse the surplus blanks. This keeps the trailing blank always ignorable and keeps the submit count truthful.

## 9. Ticket picker

**Do not use `ttk.Combobox`.** It takes a flat list of strings, which makes group headers selectable and reduces indentation to a hack. Build a custom `Entry` + `Listbox` popup — roughly 60 lines, and it gives real non-selectable headers and full control over filtering.

### Display

Grouped, with the group label as a non-selectable header and its tickets indented beneath. Each ticket line shows key (monospace) and live title. Retired tickets sit under a collapsed **"Past goals"** section at the bottom, with a match count when a filter is active.

Once selected, the row displays `PROJ-4471 · Migrate auth service to OIDC`, truncated as needed.

### Filtering

- Match on **key, title, and group label**, case-insensitive, **substring not prefix** — so `4471` finds the ticket and `oidc` finds it too.
- **A parent/group match reveals all its children,** since the children are what gets logged against.
- **A child match still renders its parent header** for context, so two similarly-named subtasks remain distinguishable.
- Unfiltered order is **most-recently-logged first** (§12). With 25 tickets the same 5 recur most weeks; the right answer should usually already be at the top.

## 10. Date handling

- One date picker for the **entire batch**, not per row. Defaults to today.
- Back-dating is the primary reason it exists (catching up on a forgotten day). Weekends and future dates are permitted without warning.
- **Changing the date preserves all typed, unsubmitted content.** This is a hard requirement — the user must be able to switch days without retyping.
- **Changing the date discards `logged` rows.** Their work is already committed to Jira, so nothing is lost, and it prevents a row locked against 6 August from sitting in a batch now targeting 7 August. Only `logged` rows are removed; `empty`, `partial`, `ready` and `failed` rows all persist across the change.

### The `started` timestamp

Fixed at **11:00 local time** on the selected date. 11:00 is chosen for being far enough from midnight that no offset or DST discrepancy can push a worklog onto the adjacent day.

Build it with `zoneinfo` so the offset resolves for *the selected date* rather than today:

```python
from datetime import datetime
from zoneinfo import ZoneInfo

dt = datetime(2026, 8, 6, 11, 0, tzinfo=ZoneInfo(cfg["timezone"]))
started = dt.strftime("%Y-%m-%dT%H:%M:%S.000%z")   # 2026-08-06T11:00:00.000+0200
```

**Never hardcode the offset string.** Poland is UTC+2 in summer and UTC+1 in winter; a literal `+0200` places January entries at 10:00. Deriving it costs no extra code and cannot be wrong. `strftime("%z")` conveniently emits the colon-free form Jira requires.

Multiple worklogs sharing 11:00 is fine — Jira permits overlapping worklogs.

## 11. Submit flow

There is no transactional bulk endpoint, so partial failure is a first-class concern rather than an edge case.

1. **Pre-flight, local only.** If any row is `partial`, abort and highlight (§8). No network calls, nothing sent. Ticket keys need no validation here — they came from a validated allowlist, so typo'd keys are structurally impossible.
2. Collect rows in `ready` or `failed` state. Skip `empty` and `logged`.
3. **POST sequentially, awaiting each.** At 3–6 requests, concurrency buys nothing and costs clean per-row error attribution and ordered UI feedback.
4. On success: store the returned `worklog_id`, transition the row to `logged`, collapse it, update the last-used timestamp for that ticket.
5. On failure: transition to `failed`, attach a human-readable reason, leave the row editable.
6. Never re-submit a `logged` row. **The submit button reads "Submit N entries" where N counts only submittable rows** — this label is what makes retry idempotent. After a partial batch it naturally reads "Submit 2 entries", and pressing it cannot duplicate the rows that already succeeded.

**Duplicate tickets within one batch are allowed** without warning. Logging two separate entries against the same goal on the same day is legitimate.

## 12. Persistence

Three separate concerns, all under `~/.local/share/jira-logger/`:

**Draft** (`draft.json`) — a *single* working draft, not one per date. Holds the selected date and every unlocked row's raw field contents. Written on a short debounce after typing stops, and again on window close. Restored at startup. `logged` rows are not persisted; their work is already in Jira.

**Usage** (`usage.json`) — maps ticket key → ISO timestamp of last successful log. Drives the picker's default ordering (§9). Updated on each successful POST.

**Credentials** — OS keyring only. Never written to either file above.

Because no secrets live in `~/.config/jira-logger/tickets.toml`, that file is safe to commit to a dotfiles repository.

## 13. Clear button

Wipes all rows and resets to 4 blank ones. The date is left as-is.

**Confirmation gate:** prompt only when at least one unlocked row *contains content*. Gating merely on "unlocked rows exist" would confirm on every single click, since auto-append guarantees a trailing blank row is nearly always present. Gating on content gives silent clearing when there is nothing to lose, and a prompt when there is.

## 14. Open item

**Per-row undo.** Locked rows already hold the `worklog_id` returned by their POST, so a delete button on a `logged` row would cost almost nothing to add and is session-scoped (no JQL required). It exists to recover from a fat-fingered `20h` instead of `2h`.

This was left undecided — the user may prefer to correct such mistakes directly in Jira, particularly now that the "what's logged today" view has been dropped. **Confirm before implementing.** If included, remember `adjustEstimate=leave` on the DELETE.

**Resolved 7 August 2026: not implemented.** Corrections are made in Jira directly. The DELETE endpoint is consequently unused, and `worklog_id` is retained on locked rows for nothing more than diagnostics.

## 15. Note outside the app's scope

Logging against subtasks is correct: Jira aggregates children's time onto the parent automatically, so the roll-up happens without ever logging to the parent directly. Worth confirming that any Jira reports or dashboards consuming this data read the *aggregate* time field rather than the parent's own time spent — otherwise the subtask hours will appear to be missing.

## 16. Acceptance checklist

- [ ] Missing config, bad TOML, absent token, and no network each produce a clear message and no window
- [ ] An unknown or invisible ticket key in the config aborts startup, naming the key
- [ ] Titles in the picker come from the API and are never read from the config file
- [ ] 4 rows on open; filling the last appends exactly one blank
- [ ] Deleting content from trailing rows collapses surplus blanks back to one
- [ ] A row with a ticket and time but no comment blocks the submit
- [ ] A row with only a comment blocks the submit
- [ ] Fully blank rows are skipped silently and excluded from both the total and the button count
- [ ] `1d` is rejected with a clear message; `1.5h` and `90m` both parse
- [ ] Submitting 4 rows where the 2nd fails leaves 3 logged, 1 editable, and the button reading "Submit 1 entry"
- [ ] Pressing submit again after a partial failure creates no duplicates
- [ ] Remaining estimate is unchanged on every logged issue
- [ ] A worklog created for a December date carries `+0100`; an August date carries `+0200`
- [ ] Changing the date preserves typed rows and removes locked ones
- [ ] Clear prompts when rows hold content, and clears silently when they do not
- [ ] Typing `oidc`, `4471`, and a parent's name each surface the expected ticket
- [ ] Retired tickets are reachable via "Past goals"
- [ ] The draft survives force-quit and restart
- [ ] `Ctrl+Enter` submits; `Enter` inserts a newline in the comment field

## 17. Implementation notes

Built 7 August 2026 as `bulklogger.py`. Where the running code departs from the
specification above, this section is authoritative.

**Name.** The product is Bulklogger — the executable, the module and the file
names all use it. Window and dialog titles read **JIRA Bulklogger**, held
separately as `WINDOW_TITLE` so the two can diverge without one leaking into the
other.

**Icon.** `bulklogger.ico`, generated from `documentation/4320180.png` at seven
sizes from 16px to 256px. It is committed rather than built, so PyInstaller
needs no image library. It is embedded as the exe resource *and* bundled with
`--add-data` for `iconbitmap(default=...)`, which covers the running window's
title bar and taskbar entry as well as every dialog. Assets are read through
`resource_path()`, which prefers `sys._MEIPASS` over `APP_DIR` — bundled
resources land in the unpack directory, unlike config, which must stay beside
the executable.

**Paths (supersedes §5.1 and §12).** Config and state live beside the
application, not under `~/.config` / `~/.local/share`: `tickets.toml`,
`credentials.toml`, `draft.json`, `usage.json`. Under PyInstaller `__file__`
points inside the unpacked temp directory, so the base directory is derived
from `sys.executable` when frozen. `credentials.toml`, `draft.json` and
`usage.json` are gitignored; `tickets.toml` holds no secrets and is shared.

**Credentials are a plain-text file, not the keyring (supersedes §4 and §12).**
The tool is distributed to several people who each run it on their own machine
with their own personal token, so the token lives in `credentials.toml` beside
the executable. This is a deliberate security downgrade from what §4 specified:
anyone who can read that file can act as its owner in Jira. It is gitignored,
`chmod 0600` is attempted, the file itself carries a "NEVER COMMIT" header, and
the sign-in dialog says where the token is going. If the threat model ever
tightens, `load_credentials` / `store_credentials` / `clear_credentials` are the
only three functions that would need to change.

**Distribution.** `build.ps1` produces a single windowed `dist\Bulklogger.exe`
(~14 MB) via PyInstaller, with `--collect-all tzdata` so the time zone database
travels with it. Config and credentials are not bundled — the exe reads them
from its own directory, so a rebuild never clobbers anyone's token.

**macOS.** `build.sh` produces `dist/Bulklogger.app`. PyInstaller cannot
cross-compile, so it must run on a Mac; `.github/workflows/build.yml` builds
both platforms on their own runners and uploads the results, which is how to get
a Mac build without a Mac. Four things differ and each is handled in code rather
than left to the build:

- **Config location.** `sys.executable` inside a bundle is
  `Bulklogger.app/Contents/MacOS/Bulklogger`; writing `credentials.toml` there
  would bury it inside the bundle, where a reinstall discards it. `_app_dir()`
  detects the `*.app/Contents/MacOS` tail and steps back out to the folder
  holding the bundle.
- **Scroll deltas.** Windows reports wheel movement in multiples of 120, macOS
  in small integers, and X11 as `Button-4`/`Button-5` with no delta at all. The
  original `int(-event.delta / 120)` floors every real macOS scroll to **zero**,
  so the row list simply would not scroll. `wheel_steps()` normalises all three.
- **Icons.** `iconbitmap` only takes `.ico`, and only on Windows. Elsewhere
  `set_window_icon` falls back to `iconphoto` with a PNG, keeping a reference to
  the `PhotoImage` so Tk does not garbage-collect it. `make_icons.py` generates
  `.ico`, `.icns` and `.png` from one source and all three are committed.
- **Data separator.** `--add-data` wants `;` on Windows and `:` elsewhere,
  hence two build scripts rather than one parameterised script.

The `.app` is unsigned, so Gatekeeper blocks the first double-click; recipients
right-click → Open once. `build.sh` prints this. Signing would need an Apple
Developer account and was not pursued.

**Theme.** `theme.py` (Mono Industrial, carried over from another project)
supplies the palette, fonts, `clam`-based ttk styling and the DWM dark title
bar. Inputs stay classic `tk` widgets rather than `ttk` so their background can
be tinted directly when a field is flagged. Native message boxes cannot be
themed and remain light — a Tk limitation, not an oversight.

**Search endpoint (supersedes §4).** `GET /rest/api/2/search` was deprecated by
Atlassian in favour of `/rest/api/2/search/jql`, which uses `nextPageToken`
rather than `startAt` and returns no `total`. The client calls `/search/jql`
first and falls back to `/search` on 404/410, so it works against either.

**`tzdata` is a required dependency on Windows.** Windows ships no IANA time
zone database, so `zoneinfo` cannot resolve `Europe/Bucharest` without it.
A missing database produces a message naming the fix rather than a stack trace.
Full runtime dependency list, in `requirements.txt`: `requests`, `tzdata`.
`keyring` was dropped along with the keyring-based credential store.

**Timezone.** `Europe/Bucharest`. The §16 DST check therefore reads: a December
date carries `+0200` and an August date `+0300`.

**Date control (§7).** Tkinter has no date widget and no third-party one was
added: a `YYYY-MM-DD` text field with `◀ ▶` day-step buttons and `Today`.

**Row count (§8).** "Exactly one trailing blank row" is bounded below by the
four rows of §7 — surplus blanks collapse to one, but the window never shrinks
below four rows total. Without this the two rules contradict each other.

**Rows area scrolls.** Six expanded rows exceed a comfortable window height, so
the row list sits in a scrollable canvas.

**Keeping the rows anchored to the top.** Three separate Tk behaviours had to be
handled before the row list would stay put. All three are in `_resync_scroll()`.

1. **A scrollregion smaller than the widget does not confine the canvas.** With
   four rows in a tall window the region is shorter than the viewport, and Tk
   will happily scroll above it — the rows slide downwards leaving blank space
   on top. Fixed by padding the region to `max(content, viewport)` so there is
   always something to confine against.
2. **`yview()` cannot detect that.** While the canvas was scrolled hundreds of
   pixels above its content, `yview()` reported `(0.0, 1.0)` throughout, because
   the fractions are relative to a scrollregion the view has left. The honest
   measurement is `canvasy(0)` — the canvas coordinate at the top of the widget,
   which should be `0` when anchored. **Assert on `canvasy(0)`, never on
   `yview()`.** A first attempt at this fix, and its tests, both used `yview()`
   and so agreed with each other while the bug stayed visible on screen.
3. **Tk keeps the old yview fraction when the region shrinks**, stranding the
   list mid-scroll after `Clear`. And `<Configure>` on the rows frame fires when
   the frame grows but *not* reliably when it shrinks, so the resync is driven
   from `refresh()` through a single coalesced idle callback rather than from
   the binding alone. `refresh()` runs on every keystroke, hence the coalescing.

**Two scrollable regions, one wheel.** The row canvas listens on `bind_all`,
which fires on the `all` bindtag — last, and for every widget in the
application. Scrolling the open ticket picker therefore moved the picker *and*
the rows behind it. The popup's listbox now takes its own `<MouseWheel>` binding
that scrolls the list and returns `"break"`, which stops the event before it
reaches `all`. Conversely, wheeling over the row area closes any open picker
first: the popup is an `overrideredirect` Toplevel positioned in screen
coordinates, so it would otherwise hang in mid-air over content that had moved
out from under it.

**Locked rows hide the status glyph.** The collapsed summary line begins with
its own `✓`; leaving the status column gridded put the glyph on a separate line
and defeated the point of collapsing.

**`--dry-run`** simulates the whole Jira side — invented titles, a per-request
delay, no network and no keyring. A row whose comment contains "fail" is
rejected, which is how the partial-failure path is exercised. It runs with no
`tickets.toml` present.

**Tests.** `test_bulklogger.py` covers parsing, config, credentials, catalogue
and error messages. `test_app.py` drives a real window against the dry-run
client and covers the checklist above. 81 tests, no network: `python -m unittest
test_bulklogger test_app`.

**Sign-in dialog visibility.** The dialog is created while the root window is
withdrawn, and Tk on Windows withdraws any Toplevel made `transient()` to a
withdrawn master. The first build therefore ran with no visible window at all on
a machine with no credentials — the single most common first launch. The dialog
now skips `transient()` unless the master is viewable, centres itself and forces
focus. `test_app.TestCredentialDialog.test_dialog_is_actually_visible` pins it.

**Permissions required (see README for the full table).** Browse Projects, so
the startup JQL search returns the configured keys, and Work On Issues, to
create the worklog. Nothing else — no undo means no delete permission, and
reading worklogs for the review tab comes with Browse Projects. Jira-wide time
tracking must also be enabled.

### Added after the first release

**Current work note.** A free-text scratchpad with no ticket and no duration,
never submitted, and deliberately *not* cleared by `Clear` or by changing the
date — the two operations that reset everything else. It persists in
`draft.json` under `current_work`.

The point is continuity rather than data entry: somewhere to park what you are
in the middle of, so tomorrow's worklog is easy to write. That makes it the one
piece of state whose whole value is surviving the actions that clear the rest,
which is why the `Clear` confirmation now says so explicitly.

It began as a three-line box above the date bar and moved to its own **Current
work** tab, full window height, on the second pass. Notes of that kind grow, and
three lines above the entry rows both cramped the note and pushed the real work
down. The tab sits between `Log work` and `Logged work`, which has the side
benefit of separating the two confusingly similar names.

**No "+ Add entry" button.** Auto-append (§8) already guarantees a trailing
blank row the moment the last one is used, so the button could never be the only
way to get a row and was never the fastest. Removed; the footer now carries only
the keyboard hint, `Clear` and `Submit`.

**Token age in the header.** `credentials.toml` records a `created` date, shown
next to the signed-in account as "token added 2026-06-26". Atlassian tokens
expire on roughly a yearly cycle, and the failure mode without this is a
mystifying 401 on a day when nothing changed. Past `TOKEN_STALE_DAYS` (330, ~11
months) the label turns amber and adds "may expire soon", turning a surprise
into a warning. Credentials written before the field existed fall back to the
file's modification time, so upgrading users see a sensible date rather than a
blank. `load_credentials` returns a `Credentials` dataclass now that there are
three fields rather than two.

**Personal state must not ship in `dist\`.** Running the exe from its build
directory writes `credentials.toml`, `draft.json` and `usage.json` beside it —
and `dist\` is exactly what someone would zip to hand out. This happened in
practice: a distributed build carried a real API token. `build.ps1` now deletes
those three from `dist\` on every build and says loudly when it did, and the
README states the two-file shipping list up front. The underlying trade is the
one recorded above under credentials-in-a-file; this is the mitigation for its
sharpest edge.

**Logged work tab.** Reverses §2's "no what's-already-logged view". The original
reasoning was about the *log-entry screen*, where a read-out would be noise
during typing. Auditing a past day for a missed or mistaken entry is a separate
job, and a separate tab keeps them from interfering: it has its own date, so
checking last Tuesday does not disturb the batch being typed.

Query is `worklogAuthor = currentUser() AND worklogDate = "<day>"` to find the
issues, then `GET /issue/{key}/worklog` per issue bounded by
`startedAfter`/`startedBefore` in absolute epoch milliseconds. Worklogs by other
people on the same issues are filtered by `author.accountId`, so the account id
is now carried on the `App` and refreshed on sign-in.

Two deliberate choices:

- **Not restricted to `tickets.toml`.** Time logged against something
  unexpected is precisely what the tab exists to catch, so scoping it to the
  configured list would hide the most interesting failure.
- **Rendered into a read-only text view, not a table.** Worklog comments are
  multi-line by design (§4), and a Treeview would truncate them to one row.

It is N+1 requests for N issues, which at 3–6 issues a day is not worth
optimising, and it runs on a worker thread with the same queue-and-poll pattern
as submit.

**Two structural consequences.** The window is now a `ttk.Notebook`, with
account and sign-out lifted into a strip above the tabs since they apply to
both. And the date control, needed twice, became a `DateField` widget; `App`
keeps `commit_date` / `shift_date` / `goto_today` / `selected_date` as
delegating wrappers so nothing downstream had to change.

**401 mid-batch.** Rather than prompting from the worker thread, the batch is
aborted: the failing row and every row after it are marked failed, the stored
token is deleted, and the message says to restart. Every remaining request would
have failed identically.

**Sign out (not in the original spec).** Atlassian API tokens expire, typically
once a year, so re-authentication has to be reachable from a running app rather
than only through the 401 path. A `Sign out` button sits in the header next to
the signed-in account — deliberately at the opposite corner from `Submit`.

It deletes the credentials file, hides the window, and reuses the same sign-in
dialog. On success the client, catalogue and titles are all replaced in place
and the window returns; row widgets are never rebuilt, so typed entries survive
untouched. The draft is written before anything is cleared. Cancelling closes
the app, since there is no signed-in state left to return to.

This drove a refactor worth noting: credential handling moved out of `main()`
into `authenticate()`, and `CredentialDialog` now verifies the token itself and
stays open on rejection, instead of the caller looping and rebuilding the
dialog. It uses `wait_window` rather than a nested `mainloop`, which is what
makes it usable both before the app starts and while it is running.

Showing the account in the header is a small side benefit: on a shared machine
it answers "whose token is this copy using?" at a glance. Jira Cloud often
withholds `emailAddress`, so it falls back to `displayName`, then to the address
that was typed at sign-in.
